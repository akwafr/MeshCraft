# Docker deployment and IPv6

Two `docker-compose` files exist, and they must not be confused:

| File | Who writes it | Content |
|---|---|---|
| `docker-compose.yml` (repository root) | us, versioned | the instance: **four** services — controller, PostgreSQL (`db`), VictoriaMetrics (`metrics`) and Caddy (TLS termination) |
| the proxy's compose | **generated by the controller** (`internal/distrib/compose.go`), never versioned | one service, the image pulled from the built-in registry, the enrolment token pre-filled |

The `metrics` service is not an inventory detail: time series are **deliberately
separated from PostgreSQL**, because interface counters captured every five seconds
across a whole fleet represent a write load Postgres accepts but makes **everything
else** pay for — inventory and log included ([[Unified monitoring and pipelines]] §3).
Like the database, it only listens on the compose network: proxies write **through**
the controller, the only service that talks to both. Its absence does not prevent
meshcraft from starting — an empty `MESHCRAFT_METRICS_URL` means "no metrics
storage", and the controller **says so** rather than failing for a service the
inventory does not need.

## 1. The proxy's compose carries a coverage, not a home site

Generating the deployment does not ask *where to plug the proxy in* but **for which sites it will be usable** — its coverage ([[Proxy]]). The endpoints are instance resources (`POST /api/proxies/compose`, `POST /api/proxies/install-script`), open to the `site_admin` with a coverage **bounded to their sites**, and to the `global-admin`, who can make it an instance proxy ([[RBAC]]). Each call issues **its own** token, since a token is single-use.

By default, a site admin gets a proxy covering all the sites they administer, and a global admin an instance proxy: in both cases, the common case is settled without ticking anything. The gesture remains: generate, paste on the host, `docker compose up -d`.

What is **really generated** today, to the comma:

```yaml
services:
  meshcraft-proxy:
    image: ctrl.example.com/meshcraft/proxy:latest
    restart: unless-stopped
    # host: required for ARP/ND scans and for receiving
    # syslog/traps on the local networks — in bridge mode, the source IP of
    # messages would be the Docker gateway's, hence unusable.
    network_mode: host
    cap_add:
      - NET_RAW              # ARP scan / Neighbor Discovery
      - NET_BIND_SERVICE     # syslog 514/udp, traps 162/udp
    environment:
      MESHCRAFT_CONTROLLER: "https://ctrl.example.com"
      MESHCRAFT_ENROLL_TOKEN: "…"
    volumes:
      - meshcraft_proxy_state:/var/lib/meshcraft   # identity + updated binary
volumes:
  meshcraft_proxy_state:
```

The state volume is not a convenience: it carries the proxy's durable identity **and** the binary downloaded during an update ([[Proxy versioning and updates]]).

> [!warning] Two gaps between this comment and the proxy's reality
> The generated compose matches this excerpt — it really is it, line for line. But two
> of its claims are false today, and they read as states:
>
> - **the tag is `:latest`, not a version.** `distrib.ImageRef` concatenates it
>   hard-coded. Pinning a version in the compose is **decided, not built**, and
>   requires two things that do not exist yet: a `:<version>` tag written by `mkoci`,
>   and a registry that **404s on an unknown tag**
>   ([[Proxy versioning and updates]] §1). It does not block updates, which
>   replace the **binary** and not the container;
> - **there is no syslog listener.** `NET_BIND_SERVICE` is needed for **162/udp** —
>   traps, shipped and validated on real hardware. The comment
>   `# syslog 514/udp, traps 162/udp` announces a listener that exists nowhere in
>   `cmd/proxy`. Mentioning it in a file the operator reads has them look for an
>   absent service, and suggests a syslog collection that never took place.

> [!important] The registry must make its index addressable by digest
> A `docker` client resolves the tag, reads the digest from the
> `Docker-Content-Digest` header, **then asks again for the manifest by that digest**.
> If the registry can only serve the index by its tag, that second request gets a
> 404: `docker pull` gets by with a **deprecated** "pull by tag" fallback (with a
> warning), but `docker compose up` fails outright —
> *failed to copy: httpReadSeeker: failed open: content at … not found*.
>
> This is a bug met for real. The index is therefore **also written as a blob** by
> `mkoci`, and a non-regression test checks it. General lesson: in a registry, every
> document is addressable by its content, the index included — the tag is only an
> alias.

### Without Docker: install script and systemd unit

The controller also generates a **POSIX install script** for hosts without Docker (minimal VM, Raspberry Pi, internal policy). It does what an operator would do by hand, but without making mistakes:

1. `uname -m` → the matching artefact among those **this** controller serves (amd64 / arm64 / armv7);
2. download, then **SHA-256 verification** against the value captured when the script was generated — a non-conforming binary is never installed;
3. creation of an unprivileged service account (`meshcraft`), state in `/var/lib/meshcraft`;
4. enrolment token written to `/etc/meshcraft/proxy.env` with mode **0600** — *never* in the systemd unit, which is world-readable;
5. hardened unit, then `systemctl enable --now`.

The unit applies the least privilege announced by [[Proxy security]]: `User=meshcraft`, only the capabilities `CAP_NET_RAW` (ARP/ND scan) and `CAP_NET_BIND_SERVICE` (syslog 514/udp, traps 162/udp), `NoNewPrivileges`, `ProtectSystem=strict`, `RestrictAddressFamilies` limited to `AF_INET AF_INET6 AF_NETLINK AF_PACKET`, and `StateDirectory=meshcraft` for the only writable path — the one where the binary of an automatic update will also be stored ([[Proxy versioning and updates]]).

The script is **idempotent**: rerun, it replaces the binary and the unit without touching the already enrolled identity (`state.json`). It is also the manual update path for those who do not enable auto-upgrade.

> [!note] No `curl | sh`
> The script embeds a single-use secret: it is **downloaded from the UI by an
> authenticated `global-admin`**, then run with `sudo sh`. A `curl … | sh` one-liner
> would assume a URL carrying the token, hence a secret in a shell history and in a
> reverse proxy's logs.

## 2. IPv6, proxy side

The proxy runs with `network_mode: host`: **it shares the host's network stack, hence its IPv6 too.** There is nothing to enable in the compose — and above all nothing to try to enable:

> [!warning] No `sysctls` in a host-network container
> Docker **refuses** any `sysctl` with the `net.*` prefix when the container does not
> have its own network namespace (`sysctl … not allowed in host network
> namespace`). Writing `net.ipv6.conf.all.disable_ipv6=0` in the generated compose
> does not "enable" IPv6: it prevents the container from starting. If IPv6 is
> disabled on the host, it is on the host that it gets fixed.

What really has to be done, on the proxy's code side — and where each point stands:

- **Dual-stack traps: shipped.** `startTrapReceiver` binds `net.ListenUDP("udp", :162)` on the **wildcard** address, which under Linux yields an `AF_INET6` socket that also accepts mapped IPv4 (`net.ipv6.bindv6only=0`, the default). The wildcard is not a shortcut: the proxy **does not know** which of its addresses a device will target, and that is exactly the question `PKTINFO` answers. It therefore asks the kernel for the **destination** address of each datagram — `IPV6_RECVPKTINFO` on a v6 socket, `IP_PKTINFO` on a v4 one, in that order because each exists only on its own family. The returned address is *unmapped* before comparison: a dual-stack socket returns `::ffff:10.42.0.67` where the controller wrote `10.42.0.67` into the device, and comparing the texts would make attribution fail depending on the mood of the host's stack.
- **What the proxy logs at startup**: the port really obtained and whether the **destination is readable** (`destination_readable`) — not the families listened on. It is the right information, and it is worth more: without a destination, a trap remains a received trap, but it can no longer **prove** which address the device sends to. A kernel that refuses both options produces an explicit warning.
- **On a host where `bindv6only=1`**, **two explicit listeners** would be needed. This is **not** handled: the single socket would fall back to v4 only, and nothing would say so other than the absence of v6 traps. It is a rare scenario and a known limit, not an established property.
- **Source IP kept as is: shipped.** A trap's sender is identified by its address, v4 or v6, normalised into a `netip.Addr` before being passed up. On the other hand, **the columns are not `inet`**: `devices.mgmt_ip`, `devices.trap_dest_addr` and the fields of the management plan are `text` ([[Database schema]]). The choice is consistent with the rest — validation lives in the code, where it can explain a refusal — but one needs to know it before writing a query that would rely on a PostgreSQL subnet operator.
- **Interface announcement: shipped.** The proxy reports its v4 and v6 addresses in CIDR, excluding loopback and link-local (`cmd/proxy/ifaces.go`) — the UI uses them to suggest ranges to scan.
- **Controller URL: shipped.** `MESHCRAFT_CONTROLLER` accepts an IPv6 literal, necessarily **in brackets** (`https://[2001:db8::1]:8080`). Every host:port read goes through `net.SplitHostPort` or `netip.ParseAddrPort` — never a split on `:`, which silently breaks on IPv6.

> [!warning] ICMP monitoring is IPv4 ONLY
> This is the dual-stack hole that matters most, because it affects the green/red
> light of the whole fleet. `cmd/proxy/monitor.go` opens
> `icmp.ListenPacket("ip4:icmp", "0.0.0.0")`, and the send loop **explicitly
> discards** every v6 target — the code says so itself: *"IPv6: to be handled with
> `ip6:ipv6-icmp`, not yet shipped"*.
>
> A consequence to know before deploying a site in IPv6: a device whose management
> address is a v6 one **is never pinged**. It does not turn red — it simply has no
> status, and a device without a status reads as a device not yet configured, not as
> a gap in meshcraft.
>
> The fix is bounded and known: a **second** `ip6:ipv6-icmp` socket, with targets
> sorted by family. It is no subtler than that — it simply has not been done, and this
> page announced it as achieved.

> [!note] No syslog collection, anywhere
> This section listed `:514/udp` and "the local status" among the proxy's listeners.
> Neither exists: `cmd/proxy` opens only the trap socket and the raw ICMP socket, and
> there is no local status HTTP server. The **syslog** channel is **decided, not
> built** in its entirety — no listener, no parser, no destination written into the
> devices. Keeping it as a target is right; describing it as a listener in place had
> people look for an absent service, and suggested that a site "that does not send its
> syslog" had a network problem.

> [!important] The built-in registry and IPv6 literals
> Docker's image reference parser only accepts an IPv6 literal **followed by an
> explicit port**: `[2001:db8::1]:8080/meshcraft/proxy:latest` is valid,
> `[2001:db8::1]/meshcraft/proxy:latest` is not. When the controller's public URL is a
> bare IPv6 address, compose generation therefore **always** adds the explicit port
> (`:443` or `:80`).
> Real recommendation: publish the controller behind a **DNS name with A and AAAA**.
> That is what makes the deployment indifferent to the address family, and it is
> needed for the TLS certificate anyway.

### IPv6 discovery: what is possible, and what is not

An exhaustive IPv6 sweep does not exist — a `/64` holds 2⁶⁴ addresses. [[Discovery]] in IPv6 therefore cannot rely on the sweep, but on:

- the local segment's **neighbour table** (Neighbor Discovery), including `ff02::1` (all-nodes): it is the useful equivalent of the ARP scan;
- **explicitly declared, small** prefixes — the threshold is `/112`
  (`discovery.MinIPv6Bits`), so a `/120` management range sweeps very well;
- LLDP and SNMP, which deliver neighbours' addresses without looking for them;
- manual addition by address, which remains the reliable way in.

> [!important] Declaring and sweeping are two distinct questions
> This page announced a refusal **at input**. The code does better, and the nuance is
> what makes the behaviour defensible: `ValidPrefix` **accepts** a `/64` — it is the
> site's real subnet, and refusing it would force the operator to lie about their
> addressing. It is the **enumeration** that is bounded, and only that: `Enumerable`
> refuses to sweep a v6 prefix wider than a `/112`, with its reason in plain words
> ("a `/64` = 1.8·10¹⁹ addresses") and the repair gesture. On the IPv4 side, the bound
> is `MaxHosts = 65536`, i.e. a `/16`: beyond that, it is a sweep counted in hours and
> declared in slices.
>
> The discovery strategy is therefore chosen **at sweep time**, not at declaration.
> Refusing at input would have made the site's real v6 subnet undeclarable, hence
> invisible in the inventory of ranges — a prefix you cannot name is a prefix you
> forget.
>
> What remains **open**: the proxy's neighbour table (NDP, `ff02::1`) is not reported.
> In the meantime, a declared `/64` is a `/64` that is not discovered — and the refusal
> message says so explicitly rather than suggesting a silent sweep.

## 3. IPv6, instance side

> [!warning] Decided, not built — the repository's `docker-compose.yml` is IPv4 only
> Nothing in this section is in place today. The versioned compose publishes
> `"80:80"`, `"443:443"`, `"443:443/udp"` in short notation, exposes the controller on
> `127.0.0.1:8080` only, and **declares no `enable_ipv6`**. The fragment below is the
> **target**, and it is kept as is for a reason: the three conditions are cumulative
> and not obvious, and forgetting one gives a deployment that looks v6 without being
> so — the costliest failure mode of this topic, because it only shows in use.

Three cumulative conditions, two of which lie outside the compose:

1. **The Docker daemon** must be able to do IPv6 — `/etc/docker/daemon.json`:
   ```json
   {"ipv6": true, "ip6tables": true, "fixed-cidr-v6": "fd00:cafe::/64"}
   ```
   `ip6tables` has been enabled by default since Docker Engine 27; it still has to be declared explicitly for earlier versions, otherwise containers have a v6 address but no return traffic.
2. **The compose network**: `enable_ipv6: true` with a ULA subnet.
3. **Dual-stack port publishing.** Depending on the daemon version, `"80:80"` publishes **only in IPv4**. We do not want to depend on the version: both families are published explicitly.

```yaml
services:
  controller:
    ports:
      - "127.0.0.1:8080:8080"
      - "[::1]:8080:8080"        # no public exposure: Caddy is in front
  caddy:
    ports:
      - "0.0.0.0:80:80"
      - "[::]:80:80"
      - "0.0.0.0:443:443"
      - "[::]:443:443"
      - "0.0.0.0:443:443/udp"    # HTTP/3
      - "[::]:443:443/udp"
networks:
  default:
    enable_ipv6: true
    ipam:
      config:
        - subnet: fd00:cafe:1::/64
```

> [!note] A ULA prefix contains only hexadecimal digits
> An earlier version of this page wrote `fd00:meshcraft::/64`, which is **not** an
> IPv6 address: `m`, `s`, `h`, `r`, `t` are not hex digits. Copied as is, Docker
> refuses the network at startup. The kind of mistake only a trial reveals, and that
> the memory of a readable name keeps alive — hence the correction to `fd00:cafe:…`,
> mnemonic **and** valid.

Points to watch on the controller side:

- **`MESHCRAFT_EXTERNAL_URL`**: preferably a DNS name (A + AAAA); otherwise a bracketed literal **with an explicit port**, for the image reason given above. This URL ends up in the generated compose, in the image reference, in the update descriptors and in the migration orders: a mistake here spreads everywhere.
- **ACME over IPv6**: Let's Encrypt validates through A or AAAA indifferently. An AAAA record that is published but not reachable **makes validation fail** even if the A works — the most common IPv6 trap in production.
- **Client address**: `X-Forwarded-For` in IPv6 contains `:`. Extraction goes through `middleware.RealIP` (chi), mounted at the head of the chain, and not through a home-made split. The controller trusts this header only because **Caddy is the only way in** — and it is the compose that guarantees it, by exposing the controller only on the loopback. Publishing port 8080 would break this assumption without touching a line of Go.
- **PostgreSQL and VictoriaMetrics** are never published: they stay on the compose's internal network, where the address family changes nothing.

## 4. Bridge mode: documented, never generated

On a host where `network_mode: host` is refused (security policy, orchestrator), the proxy runs in bridge mode with `enable_ipv6` — but **in an accepted degraded mode**: the ARP/ND scan no longer sees the local segment, and the source IP of traps becomes the Docker gateway's, which makes attributing messages to devices impossible ([[Monitoring]]). The controller does not generate this variant; it is given in documentation, with its limits, for cases where only the TCP tunnel is expected of the proxy.

The degradation is in fact **twofold**, and the second half was not stated: the proxy
does not only identify a trap by its **source** IP, it also checks its **destination**
address to prove that the return path really goes through the address written into the
device (`trap_seen_at`, migration `0023`). In bridge mode, the destination seen is an
address on the Docker network, never the one the controller wrote: proof of the return
path becomes unreachable, on top of attribution by source. A proxy in bridge mode can
therefore serve as a **tunnel** and an ICMP probe; it cannot be a **trap collector**.
